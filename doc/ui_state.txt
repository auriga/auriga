排他UIの状態管理

■ 管理対象
  pc_ui.hのpc_ui_typeはサーバー内部の画面状態であり、クライアントのUI番号とは別です。
  NPC会話、倉庫、個人間取引、露店・購買露店の開設状態は従来の管理を維持します。
  この状態はmap-server上のセッションに属し、保存DBやインター通信には追加しません。

  PC_UI_NONE        : 排他画面なし
  PC_UI_REFINE      : 精錬UI
  PC_UI_RODEX       : RoDEX受信箱（受信箱からのメール作成を含む）
  PC_UI_RODEX_WRITE : 受信箱を開かずに利用するメール作成画面
  PC_UI_BARTER      : 通常バーター
  PC_UI_EXBARTER    : 拡張バーター
  PC_UI_CASHSHOP    : キャッシュショップ
  PC_UI_STYLIST     : スタイルショップ

■ 開始と終了
  pc_ui_can_openは、開始先と現在の画面の排他関係だけを確認します。
  PACKETVER・マップフラグ・取引状態・必要アイテムなどの条件は各機能側で確認します。
  NPCスクリプトから呼ぶ画面もあるため、会話中かどうかを共通処理で一律に拒否しません。

  pc_ui_beginは、別の画面を利用中なら失敗し、同じ画面の再表示は許可します。
  呼び出し側は、対応PACKETVERと機能条件を満たした後、パケット送信前に状態を取得します。
  受信箱からの作成時は受信箱を維持し、単独作成中に受信箱を開くと受信箱状態へ移ります。

  pc_ui_endは、現在の画面と終了対象が一致する場合だけ解除します。
  バーターでは所有していたnpc_shopidも解除します。
  メールの添付や送信照会待ちは変更しません。各メール処理が従来どおり管理します。
  異種画面の古い終了通知は無視できますが、同種画面の世代識別は提供しません。

■ 操作制限
  pc_ui_blocksは、現在の画面に対応した定数ポリシーと操作マスクをビット演算で判定します。
  MOVE / ACTION / SKILL / ITEM / INTERACT / TRADE / OTHER_UIを用途別に指定します。
  精錬UIは従来の操作制限を維持し、RoDEX・バーターでは移動やアイテム操作を一律に禁止しません。
  他の排他UIを開くことは全画面で制限し、各画面自身の購入・受取要求は画面種別を直接確認します。
  その他の取引・倉庫・添付などの既存条件は残します。

  pc_ui_on_warpは、精錬・バーターを解除し、RoDEXの状態は維持します。
  別map-serverへの接続や再ログインでは新しいセッションとして初期化されます。

■ UIを追加するとき
  1. 開始要求・操作要求・終了通知を調べ、閉じたことをサーバーで確認できるかを確認します。
  2. pc_ui_typeとpc_ui_policiesへ種別・操作制限・ワープ時の扱いを追加します。
     種別とポリシーの件数が合わない場合はコンパイル時に検出します。
  3. 機能側でPACKETVERや固有条件を確認し、開始・終了・操作要求を共通管理へ接続します。
  4. 取引に必要なNPC ID・レシピID・添付情報などは機能側の情報として保持します。

  今後clif_openuiなどを実装する場合も、通信上のUI番号を内部の画面種別へ明示的に対応づけます。
  表示専用画面や終了通知を確認していない画面は、共通送信だけを理由に排他状態へ登録しません。
  未対応PACKETVERや送信引数の桁あふれ時は、パケットや状態を変更せず失敗として扱います。
  汎用パケット送信命令や未実装の画面機能そのものは、今回の変更には含めていません。
