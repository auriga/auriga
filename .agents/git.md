# Git 運用ルール

## 基本方針

- **コミット・push・PR 作成は、ユーザーが明示したときだけ行う。**
- `git config` は変更しない。
- `--force` push、`hard reset`、履歴改変はユーザーが明示した場合のみ。`main` / `master` への force push は警告する。
- `--no-verify` などでフックを飛ばさない（ユーザー明示時のみ可）。
- 対話が必要な git 操作（`git rebase -i`、`git add -i` など）は使わない。

## ブランチ

- 既定ブランチは `master`。
- 機能・作業ブランチの例: `feature/...`、`chore/...`、`fix/...`
- ユーザーがブランチ指定をしていない場合、勝手にブランチを切ったり切り替えたりしない。必要なら確認する。

## コミット

- メッセージはリポジトリの既存スタイルに合わせる（日本語の説明、または簡潔な英語。関連ファイル名を括弧で添えることが多い）。
- 「なぜ」が伝わる 1〜2 文を優先する。
- 秘密情報（`.env`、認証情報、サーバパスワードなど）をコミットしない。依頼されても警告する。
- ステージするファイルは依頼内容に関連するものだけ。キャッシュやローカル成果物（`*.cache`、ビルド生成物など）は含めない。
- コミットメッセージは HEREDOC 等で渡し、体裁を崩さない。
- `commit --amend` は次をすべて満たす場合のみ:
  1. ユーザーが amend を依頼した、またはフックが自動修正したファイルを含める必要がある
  2. HEAD がその会話で自分が作ったコミットである
  3. まだ remote に push していない
- フックでコミットが失敗・拒否された場合は amend せず、修正して **新しいコミット** を作る。

## Pull Request

- ユーザーが PR 作成を依頼したときだけ作成する。
- `gh` を使う。タイトルと本文（Summary / Test plan）を付ける。
- 作成前に `git status`、差分、`master` からのコミット履歴を確認する。
- 未 push なら `-u` 付きで push してから PR を作る。
- 完了後に PR URL を返す。

## 変更範囲

- 依頼されていないファイルをコミットに混ぜない。
- `CHANGELOG.md` の更新が必要な変更では、コミット方針をユーザーの指示に従う（同一コミット / 分離は既存慣例や指示に合わせる）。
